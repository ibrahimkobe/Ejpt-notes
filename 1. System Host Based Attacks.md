### Exploiting SUID Binaries

The success of our attack will depend on the following factors:
- Owner of the SUID binary – Given that we are attempting to elevate our privileges, we will only be exploiting SUID binaries that are owned by the "root" user or other privileged users.
    
- Access permissions – We will require executable permissions in order to execute the SUID binary.

1. `whoami` , student
2. `groups student` , its not part of any group
3. `pwd` , /home/student
4. `ls -al` , we can see that we have 2 binaries: greetings , welcome , in the welcome binary we notice a SUID permission
5. `./greetings` , we wont be able to access
6. `./welcome` , we will be able to see the message (welcome to attack defense labs)
7. `file welcome` , to tell us some information about the binary
8. `strings welcome` , it will give us some strings in the binary
9. `rm greetings`deleted the original file. This was possible because even though you couldn't execute `greetings`, you had write permissions to the `/home/student` directory that contained it.
10. `yes`
11. `cp /bin/bash greetings` **The Bait and Switch.** You copied the standard Linux shell (`bash`) into your directory and named it `greetings`.
12. `ls`
13. `./welcome` , now we have root privileges When you ran `./welcome` the second time, the binary started up with `root` privileges. Following its internal programming, it reached the instruction to execute `greetings`.
However, `greetings` is no longer the original program; it is now a copy of the bash shell. Because `welcome` called this new file while operating as root, it spawned a root-level bash shell and handed over control to you.

##### Explanation Of the Vulnerability

1. Blind Trust in a Filename

The `welcome` binary is programmed to execute a second file named `greetings`. The vulnerability exists because the developer told the program _what_ to run (the name "greetings"), but not _where_ to find it securely (an absolute path like `/opt/app/greetings`) or _how_ to verify it (checking the file's hash or owner before running it).

Because it just looks for a file with that specific name in the current directory, it blindly trusts whatever file you put in front of it.

2. Privilege Inheritance

When an operating system executes a program, any "child" processes spawned by that program automatically inherit the permissions of the "parent."

- The **Parent** (`welcome`) has the SUID bit set, so it runs as `root`.
    
- The **Child** (`greetings`) is executed _by_ the parent.
    

Because the parent is running as root, the child is instantly granted root privileges the second it is launched, regardless of who actually created or owns the child file.

3. Separation of Privileges Failure

The `welcome` binary does not drop its root privileges before calling the secondary file. A secure program would use root privileges only for the milliseconds it needs them (e.g., to open a secure port or read a locked configuration file) and then intentionally downgrade itself to a standard user before running anything else.
